# SENTINEL — API contract for the web app

Owner: Jules (`services/api/`, FastAPI). This file says **what** the web app needs. Response bodies are
the dataclasses in `pipeline/schemas.py`, serialised with `to_dict()`. MOCK examples of every body are in
`fixtures/`. The product side is in [PRODUCT.md](PRODUCT.md).

## Ground rules

- **Bind to `127.0.0.1` only.** It is reached through an SSH tunnel. No CORS wildcard: allow only the
  local web dev origin.
- **No cloud inference.** The API only calls the pipeline, and the pipeline calls the LLM only via `LLM_BASE_URL`.
- **Label isolation.** The API never reads `artifacts/manifests/evaluation.json` or label files. The
  only exception is quality reports, which are produced offline by `pipeline.evaluate` and served as
  files. Uploaded files get a **neutral call ID** generated by the server. The original upload
  filename (which may be `Stufe3_…`) is never stored next to the audio, never passed to the pipeline,
  and never returned.
- **The pipeline does not depend on the API.** `run.sh` works without it. The API is a thin layer
  over `process_call` and the artifact files.
- JSON is UTF-8 (Swiss German text) and uses snake_case, as in the schemas.
- **Errors** always have the body `{"error": "<code>", "detail": <string | list[str]>}`. Codes:
  `not_found` (404), `not_ready` (202, see below), `not_available` (404, an optional artifact does not
  exist), `invalid` (422, `detail` = the `SchemaError.errors` list), `conflict` (409), `internal` (500).

## Pipeline interface

```python
from pipeline import process_call
result: dict = process_call(audio_path: str, call_id: str)   # a CallResult as dict (schemas.CallResult)
```

- Synchronous and long-running (ASR + LLM). Run it in a worker with **one job at a time on the GPU**,
  and keep the rest in a FIFO queue.
- It never raises for stage failures. Those come back in `result["stage_errors"]`, with decision
  `review`. If it does raise, the job is recorded as an error with decision `review`, never as no_alert.
- Side artifacts are written by the pipeline and read by the API from disk, keyed by `call_id`:

| Artifact | Path | Schema |
|---|---|---|
| result | `out/results/<call_id>.json` (proposed; `run.sh` also writes the batch `out/results.json`) | `CallResult` |
| transcript | `artifacts/transcripts/<call_id>.json` | `Transcript` |
| decision trace | `artifacts/traces/<call_id>.json` | `DecisionTrace` |
| audio analysis | `artifacts/analysis/<call_id>/analysis.json` | `AnalysisArtifact` |
| snippets | `out/snippets/<call_id>/<name>.wav` | audio |
| quality reports | `artifacts/quality/<report_id>.json` | `QualityReport` |

- **Progress events (proposal for the pipeline milestone):** a keyword-only extension,
  `process_call(audio_path, call_id, *, on_event=None)`. When set, the pipeline calls
  `on_event(dict)` with `ProcessingEvent`-shaped dicts (without `seq`, which the API assigns). Until
  then, the API emits only `job_queued`, `stage_started` with `stage="asr"`, and `job_finished` /
  `stage_failed`.

## Endpoints

All paths are prefixed `/api`. `{id}` is a neutral call ID (`^[A-Za-z0-9_]+$`, validated; anything else → 404).

### Calls

| Method + path | Response | Notes |
|---|---|---|
| `GET /calls` | `200 list[CallListItem]` | All known calls. Query params (optional): `status`, `decision`, `criterion`, `variant`. Filtering is cheap, so the client may also filter. |
| `POST /calls` | `202 CallListItem` (`status: "queued"`) | `multipart/form-data`, field `file` (.wav; reject other types with 422). Optional `variant`. The server assigns the `call_id`, stores the audio under `artifacts/uploads/<call_id>.wav`, enqueues `process_call`. Several files = several requests. |
| `GET /calls/{id}` | `200 CallResult` when status is done/error; `202 CallListItem` (the inbox row) while queued/processing; `404 not_found` unknown | |
| `GET /calls/{id}/transcript` | `200 Transcript`, `404 not_available` | |
| `GET /calls/{id}/trace` | `200 DecisionTrace`, `404 not_available` | Baseline runs have no trace. |
| `GET /calls/{id}/analysis` | `200 AnalysisArtifact`, `404 not_available` | `?feature_maps=1` (**STRETCH**) computes feature maps lazily, then returns the artifact with `feature_maps_status` = ok/error. It may take seconds and is never needed by the UI. |
| `GET /calls/{id}/audio` | `200 audio/wav` | Full call audio for the synchronised playhead. Must support `Range` (HTTP 206) so the browser can seek. |
| `GET /calls/{id}/snippets/{name}` | `200 audio/wav` with `Range` support, `404 not_available` | `name` = basename of `evidence[].snippet_path`. Resolve it strictly inside `out/snippets/{id}/`: reject `/`, `..`, and anything that is not `^[\w.-]+\.wav$`. |

`CallListItem.status` comes from the job store: `queued` → `processing` → `done`. A run that finished
with stage errors is `error`, and its decision is still a real `review`.

### Live events (SSE)

| Method + path | Notes |
|---|---|
| `GET /calls/{id}/events` | All events for one call. Past events are **replayed** first, then live ones. The stream closes after `job_finished`. |
| `GET /events` | Global stream for the Inbox, covering all calls, live only (no replay). |

Wire format, one event per message:

```
id: call_MOCK_001:12
event: stage_finished
data: {"seq": 12, "event": "stage_finished", "call_id": "call_MOCK_001", "ts": "2026-10-10T14:01:46Z", "stage": "diarize", "elapsed_s": 6.1, "cached": false}
```

- The `data` body is a `ProcessingEvent`. `event` is one of `job_queued`, `stage_started`,
  `stage_finished`, `stage_failed`, `job_finished`. `stage` is one of `schemas.STAGES`. `decision` is
  set only on `job_finished`. `stage_failed` always has a `message`.
- `seq` increases per call. Clients reconnect with `Last-Event-ID: <call_id>:<seq>`, and the server
  resumes after it.
- Send a comment heartbeat (`: ping`) every 15 s.
- Re-runs triggered by a settings change emit the same events, with `cached: true` for every reused stage.

Full example: `fixtures/call_MOCK_001.events.json`.

### Settings

Files: `config/thresholds.json`, `config/keywords.json`, `config/rules.yaml`. The API speaks JSON for
all three, and converts `rules.yaml` to and from YAML. **The shapes below are proposals.** The config milestone
finalises them, and both this section and the schemas will be updated then.

| Method + path | Body / response |
|---|---|
| `GET /settings/thresholds` | `{"alarm": 0.7, "review": 0.4, "confidence_gate": 0.5}` (same shape as `DecisionTrace.thresholds`) |
| `PUT /settings/thresholds` | Same shape. 422 unless every value is in [0, 1] and review < alarm. Saves the file, then re-runs steps 6–8 for all processed calls from cache. `202 {"rerun": {"stages": ["rules", "confidence", "decide"], "n_calls": N}}` |
| `GET /settings/keywords` | `{"families": {"access": {"criterion": "credential_sharing", "terms": ["Passwort", …], "variants": {"Passwort": ["Passwörter", "Passwoort"]}}, …}, "fuzzy_threshold": 0.85}` |
| `PUT /settings/keywords` | Same shape. Families must be keys of `schemas.CRITERION_BY_FAMILY`. Re-runs step 3, then 6–8. `202 {"rerun": …}` |
| `GET /settings/rules` | `{"version": "...", "rules": [{"criterion": "credential_sharing", "enabled": true, …rule-specific params}]}` |
| `PUT /settings/rules` | Same shape. Re-runs 6–8. `202 {"rerun": …}` |
| `POST /settings/preview` (superseded by `POST /simulate`, kept for compatibility; it may be a thin wrapper) | Body: any subset of `{"thresholds": …, "keywords": …, "rules": …}`. **Does not save.** Response: `200 {"decision_counts": {"before": {"alarm": n, …}, "after": {…}}, "changed": [{"call_id", "decision_before", "decision_after", "risk_before", "risk_after"}], "keyword_hit_counts": {"<family>": {"<term>": n}}, "rule_fire_counts": {"<criterion>": n}}`. It must be fast (< 1 s for 60 calls): no ASR and no LLM, only cached transcripts and extractions. |

Concurrent PUTs return 409 `conflict` while a re-run is in progress.

### What-if, feedback and suggestions

The differentiator: an officer sees what a config change *would* do, tells SENTINEL which flagged calls were wrong, and gets
ranked, simulated suggestions. **Nothing here is ever applied automatically.** Bodies are the dataclasses in
`pipeline/schemas.py` (`SimulationResult`, `FeedbackEntry`, `SuggestionsResponse`, `AuditEntry`), MOCK examples are in
`fixtures/{simulation,feedback,suggestions}.json`. The logic is pure Python over cached transcripts and facts, so the API
only wires it up:

```python
from pipeline.simulate import load_inputs, load_raw, Simulator, patched_docs, ConfigError   # steps 3 + 6-8, no ASR/LLM
from pipeline.suggest import suggestions_response
from pipeline.feedback import make_entry, append_feedback, latest_feedback, append_audit, read_audit
```

`load_inputs()` reads `artifacts/{transcripts,traces,analysis}` and `out/results` (stage errors). The API never reads
`evaluation.json`: feedback comes only from the officer through `POST /feedback`.

**Patch** (request body of `/simulate`, and the `patch` field of every suggestion). Same idea as `/settings/preview`:

```json
{"thresholds": {"alarm": 0.8, "review": 0.45, "confidence_gate": 0.5},
 "keywords":   {"disable_families": ["splitting"]},
 "rules":      {"disable": ["credential_sharing"]}}
```

Every key is optional. `keywords` and `rules` may also carry a full document (`{"families": …}` / `{"rules": …}`) like the
`PUT /settings/*` bodies. An invalid patch (review >= alarm, unknown family or rule, unknown key) is `422 invalid` with the
`ConfigError.errors` list in `detail`.

| Method + path | Body / response |
|---|---|
| `POST /simulate` | Body `{"patch": {…}, "with_feedback": true}` (`with_feedback` defaults to true). `200 SimulationResult`. **Does not save.** Must be fast (< 1 s for 60 calls). `flipped[]` lists every call whose decision changes, with `reasons`, the patch components that `attributed_to` it, and `feedback_verdict` when the officer labelled it. `workload` is alarms + reviews per 100 calls, before and after. `feedback_check` lists labelled calls that moved the right way (`fixed`) or the wrong way (`violations`, which includes any `correct` call that flips), so the UI can warn while the officer drags a slider. |
| `POST /feedback` | Body `{"call_id", "verdict": "false_alarm" \| "missed" \| "correct", "note"?}`. `201 FeedbackEntry`. The server fills `ts`, `decision_at_feedback` (the call's current decision) and `config_version`, then calls `append_feedback` (atomic append to `out/feedback.jsonl`). `404 not_found` for an unknown call, `409 conflict` for a call that has no decision yet (queued or processing), `422 invalid` for a verdict that makes no sense (`false_alarm` on a `no_alert` call, `missed` on an `alarm`, bad note length). The log is append-only and the **latest verdict per call wins**: to change your mind, post again. |
| `GET /feedback` | `200 list[FeedbackEntry]`, the latest verdict per call. |
| `GET /suggestions` | `200 SuggestionsResponse`. `suggestions` are ranked (most feedback fixed first, then fewest other calls flipped, fewest knobs, smallest change). Each carries its patch, `fixed` / `not_fixed` calls, `collateral_flips` (unlabelled calls that would change) and the full simulated `effect`. An empty list always has a `reason` (no feedback yet, only "correct" verdicts, everything already resolved, or no change satisfies the correct-marked calls); it is not an error. Query `?max=5`. Computed on demand (< 2 s for 60 calls). |
| `POST /suggestions/{id}/apply` | **Needed for the apply flow.** Body `{"confirm": true, "note"?}`. Recomputes the suggestion `id` against the current config; `409 conflict` if the config changed since (the UI then reloads) or the id is unknown. Writes the config through the same code path as `PUT /settings/*` (`patched_docs(load_raw(), patch)` gives the three documents to save), re-runs steps 6-8, appends an `AuditEntry` (`append_audit`, `out/audit.jsonl`) and answers `202 {"rerun": …, "audit": AuditEntry}`. |
| `GET /audit` | `200 list[AuditEntry]`, newest first. Also written by `PUT /settings/*` (`action: "settings_change"`). |

Notes for implementation:
- `feedback` is passed to the pure functions as an argument: `suggestions_response(inputs, latest_feedback(), load_raw())`.
- Suggestions are fitted to a handful of officer verdicts. The body says so (`caveat`) and the UI shows it.
- Fixture mode: `/simulate` and `/suggestions` serve `simulation.json` / `suggestions.json`, `POST /suggestions/{id}/apply`
  returns 409 like uploads. `POST /feedback` works but keeps new verdicts in memory only (nothing is written to `out/`, they
  are lost when the API restarts); `GET /feedback` returns the `feedback.json` sample plus those, latest verdict per call.

### Quality

| Method + path | Response |
|---|---|
| `GET /quality` | `200 list[{"report_id", "run_id", "split", "mode", "system", "created_at", "is_mock"}]`, newest first |
| `GET /quality/{report_id}` | `200 QualityReport`, `404 not_found` |

Reports are files produced offline (the evaluate step, then a quality-report writer in a later
milestone). The API never computes metrics.

### Health

`GET /health` → `200 {"ok": true, "llm_reachable": bool, "gpu_queue_length": n, "versions": {...}}`. The UI shows a
warning dot when the LLM is unreachable.

## Fixture mode

With `SENTINEL_FIXTURES=1`, the API serves `fixtures/` instead of real artifacts:
- `GET /calls` → `calls.json`
- `GET /calls/{id}[/transcript|/trace|/analysis]` → `{id}.{result|transcript|trace|analysis}.json`
- `/calls/{id}/events` → replays `{id}.events.json`
- `GET /quality` → a one-item **list** of summaries built from `quality_report.json`
  (`[{report_id, run_id, split, mode, system, created_at, is_mock}]`), same shape as in normal mode
- `GET /quality/{report_id}` → `quality_report.json` when `report_id` matches, else 404

In fixture mode, audio and snippet endpoints return 404, uploads return 409, and every body carries
`is_mock` (or MOCK `versions`), which the UI shows as a banner. The frontend can also import the
fixture JSON directly, without the API.

Implementation notes (`services/api/`, run with `SENTINEL_FIXTURES=1 python -m services.api` on `127.0.0.1:8001`):
- `/calls/{id}/events` replays the recorded log paced at a fraction of its real gaps (`SENTINEL_REPLAY_SCALE`,
  default 0.1) so the Processing view visibly ticks. Calls without an events file get a short synthesized
  log consistent with their row and result (for example `call_MOCK_004`: asr `stage_failed`, then `review`).
- Settings start from MOCK defaults. `PUT` validates (422 on bad values) and keeps the values in memory only
  until `config/` exists, answering `202` with `n_calls: 0` because nothing is re-run. `POST /settings/preview`
  re-applies the decide.py priority order to the cached rows (a MOCK approximation).

## Versions block

`versions` (in `CallResult` and `DecisionTrace`) is `{asr, llm, prompt, rules, provider, self_hosted}`, all optional.
`provider` is the LLM provider name from `config/providers.yaml`; `self_hosted: false` means the LLM ran on a remote
provider (allowed for fictional data only), which the UI should show.

## Validation

The API should validate what it serves with `<Schema>.validate(d)` (and `validate_call_result` for
results), and log, not crash, on errors. A broken artifact is served as
`500 {"error": "internal", "detail": [...]}` so that the UI shows its error state.
